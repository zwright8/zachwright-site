Human-reviewed priorities

Three decisions, each tied to observable acceptance evidence.

The automated report supplies public evidence. The paid review adds repository-specific ordering, the smallest useful next step, and a way to tell when that step is complete.

  1. 01

    State the runtime-configuration boundary in the root README.

    The pinned report found neither a recognized root environment example nor an explicit statement that runtime configuration is unnecessary. Add a redacted .env.example that names required variables without values, or state plainly that no runtime variables are required.

    Acceptance evidence: the chosen statement or redacted example is committed at a new immutable revision and the auditor reports the environment check as met.

  2. 02

    Keep instruction and verification evidence linked as the project evolves.

    The pinned revision contains root AGENTS.md, GitHub Actions, verification guidance, and explicit risky-action boundaries. Preserve specific commands and approval limits in committed files instead of relying on local convention.

    Acceptance evidence: a later audit still links every positive instruction, verification, and risky-action finding to the exact revision reviewed.

  3. 03

    Treat the score as evidence coverage—not operational proof.

    The 90/100 result measures whether selected public artifacts were evidenced. It does not establish that setup instructions are correct, workflows pass, agent behavior is reliable, or production use is safe.

    Acceptance evidence: the score always appears with the report's inspection limits and no claim beyond the public files inspected.

Acceptance check

The sample uses the same boundaries promised to a buyer.

  • Repository and immutable revision match the automated report.
  • Markdown and JSON deliveries name the same repository and revision.
  • Every positive automated finding retains a public evidence link.
  • The summary contains no more than five repository-specific priorities.
  • Each priority names a bounded next step and acceptance evidence.
  • No private, personal, payment, credential, or customer data appears.

Inspection limits

The audit does not clone or execute repository code, inspect private settings, validate documentation accuracy, test production behavior, or perform vulnerability, security, privacy, legal, or compliance work. Missing evidence means only that the artifact was not evidenced in the scanned snapshot.
